## 1 课题背景与任务

### 1.1 课程要求与整机目标

课程要求综合运用语音识别、语音合成、副语言信息感知与自然语言对话，在树莓派上实现一个软硬件结合的语音交互系统。本组选题为“离线复诊登记助手”：老年患者对着树莓派说出复诊的科室、日期和时段，系统在本地完成多轮问答与模拟登记，全程不联网。整机分为五个模块：A 负责音频采集、语音活动检测、WeNet 流式识别与本地说话人匹配；B 负责自适应端点检测；C 负责口语理解、字段提取和本地 FAQ；D 负责多轮对话管理与本地登记；E 负责Tacotron2 合成、播放和整机联调。

在这条链路里，D 处在“理解之后、播报之前”的位置。C 每轮只给一次结构化的理解结果，E 只负责把 D 给的文本读出来，因此“这一轮到底该问什么、能不能保存、下一轮端点该按开放式还是是非式处理”这些问题，都必须由 D 回答。这也是本模块的工作重点。

### 1.2 D 模块的任务

D 模块的任务可以拆成四句话：接收 C 的意图、字段和问答结果；维护一份登记草稿和它的确认状态；决定下一轮是补问、澄清、复述确认还是保存；在确认有效时把模拟登记写入本地数据库，并把回复文本交给 E。方案里还要求 D 给 B、C 提供本轮问题上下文，给 E 提供回复文本，并在依赖未就绪时用符合真实接口的模拟事件先把流程跑通。

## 2 需求分析与总体设计

### 2.1 使用场景与约束

使用者是复诊的老年患者，场景有三个特点。第一，表达短：很多回答只有“下午”“还是上次那位”几个字，离开当前问题就无法解释。第二，容易改口：说错日期、临时换科室很常见，系统必须能只改一项而不推翻整份登记。第三，对重复和等待敏感：同一句话被反复追问会让人不耐烦，播报没听清时需要能重说，而不是重新开始。

工程上的约束是离线与资源有限。树莓派上没有稳定的网络，数据库只能是本地文件，模型和词表都要提前放到板上；同时整机对时延敏感，D 的每轮决策应在毫秒级完成，不能引入额外的服务调用。

### 2.2 与相邻模块的接口

D 与其余模块之间只有事件，不共享内存。图 1 给出 D 在整机一轮中的位置：C 给理解结果，D 给 E 播报文本，同时把下一轮的阶段、问题类型和期望字段发给 A、B、C；E 播完后回传结果，D 才允许进入下一轮或结束。

### 2.3 设计原则

实现遵循五条原则，后文的很多细节都是它们的直接结果。

- 事件驱动：D 不直接读麦克风、不直接调合成，输入输出都是事件，因此可以在笔记本上回放，也可以先于硬件联调。
- 状态集中：一次登记的全部状态放在草稿对象里，策略函数只做判断，不散落全局变量，便于回放和单元测试。
- 值来源可追：每个字段记录 value、raw、source 和 status，能回答“这个科室是用户说的还是上次的”，为历史继承和错误分析提供依据。
- 幂等写入：一次确认只允许一条记录，重复确认复用已有结果，避免网络重试或播报重发造成的重复登记。
- 可回放：同一组用例在基线与改进组上各跑一遍，日志与指标可复现，结论不依赖人工观察。

## 3 状态与字段设计

### 3.1 槽位模型

一次复诊登记由四个槽位组成：科室、日期、时段为必填，医生在“用户指定”或“档案继承”时随本次登记一起确认。科室和医生的值用组内词表 ID，日期统一为 YYYY-MM-DD，时段只用morning 与 afternoon 两个值，显示时再换成中文。

单个槽位除了规范值，还记录原表达、来源、状态、候选和最近更新轮次。状态是整个模块的关键抽象：它决定这个值算不算“已填”、能不能进入确认、要不要再问一次。

| 状态 | 是否算已填 | 出现场景 | D 的处理 |
| --- | --- | --- | --- |
| missing | 否 | 还没有值 | 按固定顺序补问 |
| ok | 是 | C 给出明确值 | 用于复述与保存 |
| ambiguous | 否 | C 返回候选、value 为空 | 定向澄清，或退回开放式重问 |
| candidate | 是 | 档案历史值带入 | 随本次复述一起确认 |
| needs_check | 否 | 换科室后原医生不再属于新科室 | 追问是否指定医生 |
| skipped | 否（不阻塞） | 用户明确说“不指定” | 不再追问，也不写入记录 |

### 3.2 草稿与版本

一份草稿对应一次登记，持有 session_id、registration_id、档案、阶段、槽位、版本号和确认快照。版本号 revision 的规则很简单：任何会改变登记内容的操作都会让它加一，同时把旧快照清空。这条规则把“用户改口后旧确认不能再生效”变成了结构性保证，而不是靠每个分支记得手动清理。

### 3.3 确认快照

确认快照记录四样东西：生成这条复述时的草稿版本、这条复述的 reply_id、预期用来确认的用户轮次，以及该回复是否已经播完。保存前同时检查三个条件：

1. 轮次一致：确认事件必须落在预期的确认轮次上，上一轮的“对”不能拿来确认新内容；
2. 版本一致：复述之后草稿没有再被修改，否则说明用户改了口，需要重新复述；
3. 播报完成：这条复述确实已经播完，避免“用户还没听到就确认”或“播报失败却已写库”。

三个条件缺一不可，任一不满足都不会写库，而是按当前草稿重新复述并等待新的确认轮次。这样，改口、重复确认、迟到消息和播报失败四种情况可以共用同一条判断，代码里不需要为每种情况单独写一套保护。

### 3.4 数据字典

| 对象 | 字段 | 说明 |
| --- | --- | --- |
| 草稿 | session_id / registration_id / profile_id | 会话、登记编号、当前档案 |
| 草稿 | phase | idle、collecting、confirming、ended |
| 草稿 | revision / snapshot / reprompt_count | 版本、确认快照、连续未听清次数 |

## 4 对话策略与状态机

### 4.1 状态机

登记状态从待机进入字段收集，字段齐全后进入等待确认，确认有效则写入并结束；取消可以直接结束当前草稿，更正和否认会把流程拉回收集或进入新一轮确认。状态机与动作的对应关系见表 4 与图 2。

| 当前事件 | 状态机的处理与输出 |
| --- | --- |
| 有字段待补充 | 写入本轮明确且有效的字段；有影响本次登记的疑点先澄清；否则按预定顺序问下一个缺项 |
| 字段齐全 | 生成字段快照与复述文字，进入等待确认，下一轮问题类型设为 yes_no |
| 确认或改口 | 快照版本一致且已播完则提交保存；明确更正则改字段并重新复述；只说“不对”则进入纠正询问 |
| 中途咨询 | 用 C 返回的 FAQ 答案回复，保留草稿，播报后接回原来的补问或确认 |
| 无输入或无法理解 | 保留草稿，用较短话术重问当前字段；达到重问上限后提供退出 |
| 明确取消 | 结束草稿并给出取消反馈，不写库；与字段否认区分开 |

### 4.2 补问选择

补问顺序固定为科室、日期、时段、医生。每一轮先扫描这个顺序，找第一个“必填但未填”、“有歧义”或“待核”的字段，再根据字段和原因选择问法：科室和时段用定向短问，日期用开放式提问，歧义日期改用带候选的定向澄清，换科室后的医生则说明原因并允许“不指定”。固定顺序的好处是行为可预测、评测可复现；代价是不做信息增益排序，这一点在后续优化中讨论。

### 4.3 复述与确认

字段齐全后，D 用规范值拼出一句完整复述，例如“为您登记复诊：康复科张医生，12月3日下午，对吗？”，同时把下一轮上下文标为 confirming 和 yes_no。用户说“对”才进入保存；说“不对”时先问“需要修改哪一项”，避免把对某个字段的否认误判成取消整个登记。

复述文本尽量短、把科室医生和日期时段分成两个短语，便于 E 在关键信息之间插入停顿；日期用“12月3日”而不是完整 ISO 串，减少合成前端的读法问题。

### 4.4 历史继承

历史继承分两级。第一级是建草稿时的隐式继承：档案里有上次科室和医生、而本轮草稿还没有这两项时，把它们写成 candidate，随本次复述一起确认。第二级是用户明确说“还是上次那位”时的显式继承：只有当档案能给出唯一且与科室相符的医生时，才把科室和医生整体采用；档案缺失或医生不唯一时不猜，继续按字段提问。

两级继承的区别在于“谁承担确认责任”。隐式继承的值仍要经过复述确认，用户说“对”才生效；显式继承是用户的明确指令，可以直接使用，但如果同一轮里用户还说了别的科室或医生，以用户本轮的表达为准。

### 4.5 局部更正与字段依赖

用户改日期或时段时，只替换对应字段并重新复述，其余字段保持不变。改科室要复杂一些：医生属于某个科室，换了科室后原来的医生可能不再适用。D 在写入新科室后检查医生归属，若不相符就清空医生并标记待核，然后追问“换到骨科后，原来的医生不再适用。请问还要指定医生吗？可以说不指定”。用户说不指定时，医生记为 skipped，既不阻塞确认，也不会写进记录。

这条规则正是基线缺少的部分。基线只做“替换字段”，不做依赖检查，因此在换科室用例中会把康复科的张医生带到骨科，产生一条字段不一致的记录。第 7、8 节会给出对应数据。

### 4.6 歧义澄清

老年人常说“周五”“下个月”，周次或月份不清楚。C 对这类表达返回 ambiguous 和候选，D 若开启澄清，就用候选做定向追问：“您说的是哪一周的周五？本周五（11月27日）还是下周五（12月4日）？”用户只需说“下周五”即可收敛。基线不做澄清，只能退回开放式“请问您想约哪一天”，用户往往重复“周五”，多花一轮且容易反复。

### 4.7 异常处理

| 异常 | D 的处理 | 验证用例 |
| --- | --- | --- |
| 没有听清 / 识别失败 | 保留草稿，重问当前字段；连续超过 2 次才结束 | c10_no_input |
| 播报失败 | 保留草稿与快照，用新 reply_id 重发同一段文本 | c11_playback_retry |
| 写库失败 | 保留草稿，提示再说一次确认；重试成功后仍只有一条记录 | c12_save_failure |
| 重复确认 | 已保存则回“已经保存过”，不再写库 | c08_duplicate_confirm |
| 迟到旧轮 | turn_id 小于已处理轮次的消息直接忽略 | c13_late_turn |
| 明确取消 | 结束草稿，不写库 | c07_cancel |

### 4.8 工程日志

每轮都会往 dialog_log 写一条记录，包含会话、轮次、阶段、动作和细节 JSON。细节里能看到本轮写入的槽位、草稿版本、确认被拒绝的原因、保存是否新建等信息。回放时还会把完整事件序列写成 JSONL，出问题时可以直接定位到“哪一轮、哪个字段、为什么”。

## 5 本地登记与一致性

### 5.1 表结构与写入

本地库用 SQLite，单文件、无服务、随工程拷贝。registrations 表的 registration_id 是主键，另有 session_id、profile_id、department、doctor、visit_date、period、created_at、快照与来源字段；dialog_log 记录每轮动作。写入前先按 ID 查询，存在则直接返回“已存在”，不存在才插入并在成功后提交。

```
existing = self.get_registration(draft.registration_id)
if existing is not None:
    return draft.registration_id, False    # 重复确认：复用已有结果
try:
    cur = self.conn.execute("INSERT INTO registrations (...) VALUES (...)", (...))
    self.conn.commit()                      # 提交成功后才允许播报“已登记”
except sqlite3.IntegrityError:
    self.conn.rollback()                    # 并发或重复提交：以已存在记录为准
    return draft.registration_id, False
```

### 5.2 一次确认对应一次登记

这条约束由三层保证：策略层只在快照三条件满足时才调用保存；存储层用主键唯一约束兜底；异常路径先回滚再按“已存在”处理。评测里专门用 c08 和 c13 两条用例检查：保存后再说一次“对”，以及保存后再投递上一轮的确认事件，库里都仍然只有一条记录。三次运行下来，重复写入行数均为 0。

### 5.3 事务顺序与失败恢复

顺序是“先写库、后播报”。如果反过来的话，播报成功而写库失败，用户会以为登记完成，这是不可接受的。写库失败时草稿与快照都保留，D 回一句“保存没有成功，请再说一次确认”；用户再说“对”，快照的轮次被重新绑定，重试成功后仍然只有一条记录。

### 5.4 来源记录

每条记录的 source_json 保存每个字段的来源，例如 {"department": "history_ref", "doctor": "history_ref", "date": "user", "period": "user"}。这样在复盘“为什么这条登记是康复科”时，可以直接回答是用户说的、档案继承的，还是用户引用上次记录得到的。

## 6 实验设计

### 6.1 基线与改进组

方案要求先做空表单基线，再加入历史继承、局部更正和按字段澄清。为了让对照可解释，两组共享同一份词表、档案、C 的解析规则、确认话术和保存逻辑，只切换三个开关：

| 配置项 | 固定顺序基线 | 历史继承与按字段澄清 | 作用 |
| --- | --- | --- | --- |
| inherit_history | 关闭 | 开启 | 是否读取档案的上次科室与医生 |
| clarify_ambiguous | 关闭 | 开启 | 歧义值是否用候选定向澄清 |
| check_slot_dependency | 关闭 | 开启 | 换科室后是否检查医生归属 |
| max_reprompt | 2 | 2 | 连续没听清的重问上限 |
| confirm_requires_playback | 开启 | 开启 | 确认前是否要求播报完成 |

此外还保留一组“只开关历史继承”的配置，用于把轮数变化归因到档案复用而不是澄清策略；评测脚本通过 config_override 支持这组可选对照。

15 条用例覆盖方案要求的全部场景，并按四类分组。每条用例写明预期字段、预期记录条数和轮数上限；基线换一套用户说法（steps_baseline），因为系统问法不同，用户的回答自然也不同。

### 6.3 指标口径

- 登记成功率：计划完成登记的任务中，正确保存且字段与目标一致的比例；取消用例以“退出成功、记录未写入”作为验收。
- 用户轮数：按任务统计用户发言轮数，报告成功任务的中位数、均值与样本数。
- 重复询问次数：同一字段被连续追问的次数，不含第一次。
- 关键字段正确率：所有用例的预期字段逐项比对，得到正确字段数 / 总字段数。
- 重复写入：同一 registration_id 的多余记录条数，正常应为 0。

### 6.4 可复现性

回放不依赖真实时间与随机数：参考日固定为 2026-11-24，轮次由脚本推进，播报结果由回放引擎按用例要求回传，因此同一份代码与用例可以得到同样的结果。评测命令与输出目录见附录 B。

### 7.3 典型用例分析

（1）沿用历史。c03 中用户只说“还是上次那位，下周四下午”，改进组一次复述即完成，两轮写完；基线不读档案，先问科室，用户补“康复科，张医生”后才复述，三轮完成。c15 换成骨科档案，结论相同。这两条直接对应方案里“历史继承是否减少患者需要说的话”的问题。

（2）歧义澄清。c09 中用户说“周五下午”，改进组用“本周五还是下周五”一句问清，第三轮保存；基线退回开放式提问，用户重复“周五”，第四轮才靠用户自己说出“12月4日”收敛。改进组省一轮，且没有重复询问。

（3）换科室。c05 中用户先说“康复科张医生”，随后“换成骨科”。改进组清空张医生并追问，用户答“不用了”，第四轮保存，记录为骨科、未指定医生；基线保留张医生直接保存，记录变成“骨科 + 康复科张医生”，字段检查失败。

（4）异常恢复。c11 首次播报失败后，D 用新 reply_id 重发，第二轮确认仍能保存；c12 第一次写库失败，草稿保留，用户再说“对”后成功，且只有一条记录。这两条说明“先写库后播报”“快照三条件”在两个方向上都没有漏。

### 7.4 稳定性

14 项单元与集成测试覆盖事件校验、槽位依赖、快照失效、唯一约束、继承、取消、FAQ 插入、过期确认、全用例回归和基线退化检查。三次评测运行中，改进组始终 15/15，重复写入始终为 0，说明结果不依赖运行顺序或残留数据库——评测脚本每次会重建基线与改进组的库。

## 8 错误与失败分析

### 8.1 基线为什么在换科室上出错

基线只做字段替换：新科室写入后，医生槽位仍是上一次的值。复述里出现“骨科张医生”，但张医生属于康复科，这条记录在业务上不成立。改进组在写科室时检查医生归属，把不相符的医生清空并标记待核，宁可多问一句也不写错。这个对比说明“字段之间有关系”这件事不能只靠保存前的整体检查，必须在字段更新时立即处理。

### 8.2 改进组的代价

改进不是没有成本。换科室时多问一句医生，平均轮数从 3.33 升到 3.67；歧义澄清依赖 C 给出候选，如果 C 只返回 ambiguous 而没有 candidates，D 只能退回开放式提问；历史继承依赖档案正确，档案错了会把错误值带进复述——虽然复述确认能拦住一部分，但仍会增加一次改口的轮次。

### 8.3 仍然存在的风险

- C 的歧义判断不稳定时，D 的澄清话术可能没有候选可用，需要在 C 侧保证候选字段。
- 老年口音和语速造成的字段错误，D 只能通过复述确认发现，不能在理解层纠正。
- 播报超时或设备忙时，当前只做一次重发；真实设备上可能需要退避与提示音。
- 档案与说话人匹配错误时，继承的科室医生会整体偏移，需要 A 的匹配阈值配合。
- 本地库没有做断电恢复测试，树莓派异常掉电时的事务完整性待验证。

### 8.4 与真人评测的差距

本轮所有用户话术由组员编写，属于“结构化回放”，能验证状态机和接口，但不能替代真人评测。方案里要求的组员初测、老年志愿者评测和树莓派实机耗时都还没有做；报告中的轮数与成功率只反映脚本化场景，真实场景下老年人的重复、停顿和改口会更复杂。这一点在交付材料里也做了标注，避免把回放结果当成真人结论。

方案把交付分成三次汇报。本轮把三次汇报要求的内容一次性做成了可复跑的材料，日期节点仍按课程日历：11 月 29 日初步方案、12 月 5 日最终方案、12 月 19 日最终汇报。

| 12 月 5 日 | 历史继承、字段更正、歧义澄清；接 C 与 E | c03/c15/c04/c05/c09 用例、播报与写库失败恢复、接口日志、初步对照 | 文本链路完成，真实 C/E 待联调 |
| 12 月 19 日 | 冻结策略与档案，留出场景评测，覆盖 FAQ/改口/取消/重复确认 | 15 条用例评测、完整流程与纠错演示、演示视频 | 完成（实机待联调） |

联调时有四点需要和相邻模块确认。第一，turn_id 由 D 在 TURN_CONTEXT 里给出下一个轮次，C 和 E 都按这个号回传，避免各算各的。第二，reply_id 一条回复一个，播报失败重发必须换新 ID，旧 ID 的迟到消息由 D 忽略。第三，E 的 completed 是“可以确认”的前提，播放没结束就不该收到确认。第四，registration_id 是幂等的唯一依据，断网重启后按它查库即可判断是否已经写过。

依赖未就绪时，D 用三件事保证可以先跑：用 C 的文本替身生成同结构事件；用回放引擎自动回传播报结果；用固定参考日消除相对日期的不确定性。等真实 C、E 接上，替换事件来源即可，策略代码不需要改。

## 10 总结与后续工作

本报告完成了 D 模块从设计到评测的闭环：状态与字段模型、状态机与话术、历史继承、局部更正与依赖检查、歧义澄清、本地登记与幂等、异常恢复，以及基线与改进组的对照。结果是：改进组 15/15 通过、字段全对、重复写入 0、继承类轮数从 3 降到 2、歧义类从 4 轮降到 3 轮并消除重复询问；代价是换科室场景多问一句，平均轮数略增。

这一轮最大的体会是“状态设计比话术重要”。同样的问法，只要把值来源、草稿版本和确认快照设计清楚，改口、重复确认、播报失败、迟到消息都能用同一条规则处理；反过来，如果只在分支里打补丁，很容易出现“改了日期却用旧快照保存”这类隐蔽错误。

后续工作分三步：先在整机上接通真实 C、E 与树莓派音频，补齐实机耗时与播报门控；再邀请组员和老年志愿者做真人评测，检验复述确认与重问策略；最后在状态跟踪上引入置信度与轻量模型，把规则策略替换为可学习的澄清选择。具体方案见同批提交的《个人分工、模块作用与后续优化创新方案》。
