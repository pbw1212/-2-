## 一、我的分工

### 1.1 负责范围

本组选题是“离线复诊登记助手”，五名成员分别负责音频与识别（A）、端点检测（B）、口语理解与本地问答（C）、多轮对话管理与本地登记（D）、语音合成与整机集成（E）。我负责 D 模块，具体包括六件事：

1. 对话状态设计：定义登记草稿、槽位、值来源、确认快照和状态机，保证“改口后旧确认失效”“一次确认只写一条”这类约束有结构上的保证。
2. 对话策略实现：决定每一轮是补问、澄清、复述确认还是保存，维护历史继承、局部更正、科室-医生依赖检查、中途 FAQ、取消与重问上限。
3. 本地登记：用 SQLite 保存确认后的模拟登记，实现 registration_id 唯一约束、重复确认复用、写库失败保留草稿。
4. 接口约定：在《全组联调总方案》基础上与 C、E 对齐 NLU_RESULT、REPLY_REQUEST、PLAYBACK_RESULT、TURN_CONTEXT 的字段与轮次规则。
5. 独立可运行：在 C、E、树莓派都未接通时，用规则版 NLU 替身与自动播报回传把完整流程先跑通，供其他模块对照。
6. 评测与材料：构造 15 条回放用例、基线与改进组对照、14 项测试，并整理三阶段交付、接口样例、代码讲解与本报告。

### 1.2 与组内其他模块的协作

D 处在 C 与 E 之间，协作接口最多。我对外承担的约定可以概括为“三个输出、两个输入”：

- 给 C：TURN_CONTEXT 里的 dialog_phase、question_type、expected_slots 和 reference_date，让 C 能用当前问题解释“下午”“改成周五”这类短答。
- 给 B：question_type（open / targeted / yes_no）与 expected_slot，让端点检测知道本轮是开放式长句还是是非式短答。
- 给 E：REPLY_REQUEST 的 reply_id、reply_text 和 action，E 只负责读法和播放，不解析业务字段。
- 从 C 收：NLU_RESULT 的意图、字段、状态和 FAQ 答案；按 turn_id 去重、忽略迟到轮次。
- 从 E 收：PLAYBACK_RESULT 的完成或失败；只有 completed 才允许把回复视为“用户已听到”。

### 1.4 我做的几个工程决策

- 先定状态再写话术：把槽位状态（missing / ok / ambiguous / candidate / needs_check / skipped）先定死，话术只是状态的渲染，避免“话术对了但状态乱了”。
- 用事件而不是函数调用串模块：五类事件与接口规范一致，因此可以在笔记本上回放，也可以在树莓派上换成队列，不需要改策略代码。
- 规则先行、数据后补：在真实语音和老年样本不足的情况下，用规则版 NLU 替身把流程与接口先跑通，等 C 接上再替换事件来源。
- 评测与实现同批交付：每个功能都配一条用例，指标由脚本统计而不是手抄，报告里的数字可以用一条命令复现。

## 二、D 模块在系统中的作用

### 2.1 整机链路中的位置

整机一轮的顺序是：D 生成下一轮上下文 → E 开启监听 → A 流式输出给 B → B 决定轮末 → A 最终转写给 C → C 把理解结果给 D → D 生成回复 → E 播报并回传结果。D 处在这条链路的中间，前后都是异步事件，因此它既是业务状态的唯一持有者，也是轮次的调度点：没有 D，C 不知道这一句“下午”是在回答哪个问题，E 也不知道下一句该说什么。

### 2.2 对其他模块的价值

对 C：D 提供当前问题类型和期望字段，让 C 能解释依赖上下文的短答。C 的文档里明确写了“D 提供上一轮所问的信息”，D 的 TURN_CONTEXT 就是这句约定的落地。

对 B：D 的 question_type 直接决定端点策略。确认轮是 yes_no，用户一个“对”就该结束；补问科室是 targeted，用户说“康复科”就完整；开放式提问则需要更长的静音容忍。B 的自适应端点如果拿不到这个信号，只能对所有轮次用同一个阈值。

对 E：D 把回复拆成短句、把关键字段放在一起，E 只需处理读法和停顿；reply_id 让 E 的播放队列和 D 的确认快照能对上，播报失败时也换新 ID 重发。

对 A：D 的 expected_slots 可以作为热词提示（例如本轮期望“科室”，就把科室词表加到偏置里），这也是 A 文档里提到的可选优化。

### 2.3 对使用者的价值

对老年复诊患者，D 的作用不是“多问几句”，而是“少说几句、说错能改、改完能确认”。历史继承把“康复科、张医生、下周四下午”压缩成“还是上次那位，下周四下午”；局部更正让患者只说“改成下周五”而不必重复全部信息；复述确认用一句完整的话把结果说回去，让听不清或记不住的患者有机会纠正；重问上限和短话术避免“一次没出声就被结束”。

### 2.4 对课程目标的支撑

课程要求掌握自然语言对话的基本算法并搭建语音对话系统。D 模块把“对话方法”落到两个具体问题上：任务型对话的状态跟踪与对话策略。前者对应槽位、来源与确认快照，后者对应补问选择、澄清与确认；同时用基线与改进组的对照回答“历史继承是否真的减少了交互成本”，这也呼应了课程对实验设计的要求。

### 2.5 如果去掉 D 会怎样

一个直观的反事实：C 每轮只输出意图和字段，没有 D 就没有人记住上一轮问了什么，“下午”“对”“改成周五”都无法解释；E 没有回复文本可播；数据库没有确认条件，重复播报或网络重试会写出多条重复登记；B 拿不到问题类型，只能对所有轮次用同一端点阈值。换句话说，D 把“一次登记”从若干条独立的理解结果，变成了一个有状态、可确认、可回滚的任务。

## 三、设计中的关键取舍

### 3.1 规则状态机还是端到端生成

课程提供了 seq2seq 对话机器人样例（青云、小黄鸡语料），但复诊登记是有明确业务字段和确认责任的任务型对话，生成式回复无法保证“科室、日期、时段”逐项正确，也无法保证写库前一定经过确认。因此首版选择有限状态机 + 规则 + 模板：可解释、可回放、离线可跑，缺点是话术不够自然。这个取舍与 Bohus 与 Rudnicky 在 RavenClaw 中“任务控制与错误恢复优先”的思路一致。

### 3.2 固定顺序补问

补问顺序固定为科室、日期、时段、医生，行为可预测、评测可复现，代价是不做信息增益排序，某些场景会多问一句。对老年用户来说，固定的提问顺序本身也是一种可预期的节奏，所以首版接受这个代价，把“问哪一个更划算”留到后续优化。

### 3.3 字段级来源与快照版本

每个字段记录 value、raw、source、status，每次修改推进草稿版本并使旧快照失效。这套设计比“只存值”多写了一些代码，但换来三个直接好处：能回答值的来源、能判断改口是否发生、能把“旧确认不能保存”变成结构性保证。

### 3.4 SQLite 与幂等

树莓派离线、资源有限，SQLite 单文件最合适；registration_id 唯一约束比“应用层判断是否重复”更可靠，因为断电、重复投递、并发重试最终都会落到同一条约束上。

## 四、后续优化方案

### 4.1 近期：联调前必须补齐

| 事项 | 做法 | 验收标准 |
| --- | --- | --- |
| 接真实 C | 用 C 的 NLU_RESULT 替换规则替身，保持字段不变 | 同一批用例在真实 C 上通过率不低于文本替身 |
| 接真实 E | 用 PLAYBACK_RESULT 替换自动回传，验证播报门控 | 播报未完成时确认不写库；失败后能重发 |
| 板端耗时 | 记录每轮 D 的处理时间（策略 + 写库） | 单轮处理 P90 在毫秒级 |
| 断网重启 | 重启后按 registration_id 查库，验证不重复写 | 同一登记只出现一条 |
| 日志统一 | 与 A/B/C/E 统一 session_id、turn_id、reply_id | 能按一轮串起五个模块的日志 |

### 4.2 中期：把规则策略升级为可学习策略

（1）状态跟踪。现在槽位值直接取 C 的确定结果；下一步可以把 C 的置信度、历史候选和上下文一起做融合，低置信度时保留候选而不是直接写入。TripPy 的“从用户输入、系统记忆、已有状态三处复制值”的思路可以借鉴：把档案历史当作“系统记忆”，把当前轮当作“用户输入”，把草稿当作“已有状态”，三者不一致时触发澄清。

（2）澄清选择。现在是“按固定顺序问第一个缺项”，下一步可以用信息增益或期望交互代价来选择字段：优先问那些能排除最多歧义、或用户最容易回答的字段。评价指标仍是成功任务轮数与重复询问次数，和这一轮的对照口径保持一致。

（3）历史继承的置信度。现在只要档案存在就继承；下一步用 A 的声纹相似度做阈值，低于阈值时请用户选择档案，并在复述里说明“按上次记录”。同时可以加时间衰减：半年前的记录只作为候选，不作为默认值。

（4）对话修复。把否认、打断、超时统一成“重说—纠正—退出”三选一：用户说“不对”时，先问改哪一项；连续两次没听清时，给出“再说一次 / 换种说法 / 先不登记”三个选项，而不是直接结束。

（5）老年友好。语速偏慢、关键字段单独成句、复述时先科室医生后日期时段；对“听不清”的情况提供逐字段复述（只重复日期），避免整段重播。

### 4.3 长期：从课程原型走向可用系统

- 跨会话档案：把模拟档案换成可维护的患者档案，登记结果可导出，供医院系统对接；离线时本地缓存，联网后同步。
- 多模态补充：树莓派接小屏，显示大字表单与候选按钮，听不清时可以看；对听力下降的用户提供“看+听”双通道。
- 评测体系：从结构化回放扩展到真人任务，按 PARADISE 的任务成功与交互成本口径统计；建立留出集，冻结配置后再评测。
- 可解释与可审计：每次登记保留值来源与确认快照，出现争议时可以回放整段对话。

### 4.4 优化项与验证指标

| 优化 | 现在 | 改进后 | 验证指标 |
| --- | --- | --- | --- |
| 状态跟踪 | 取 C 的确定值 | 置信度融合 + 候选保留 | 字段正确率、澄清轮数 |
| 澄清选择 | 固定顺序 | 信息增益选择字段 | 成功任务轮数、重复询问 |
| 历史继承 | 档案存在即继承 | 声纹阈值 + 时间衰减 | 继承正确率、错继承率 |
| 对话修复 | 重问上限后退出 | 三选一修复 | 任务放弃率、恢复成功率 |
| 播报策略 | 整段播报 | 按字段分句 + 局部重播 | 关键字段听清率、开播延迟 |

## 五、工程层面的创新点

需要说明：这些是本课程项目内的工程改进，不是学术意义上的新算法。它们的价值在于把“对话系统容易出错的地方”变成可检查、可复现的约束，并与基线做对照。

### 5.1 字段来源追踪 + 确认快照三条件

常规做法是保存一份表单值，确认时直接写库。这里给每个字段记录来源（用户 / 历史 / 显式引用），并让确认快照绑定草稿版本、确认轮次和播报完成三个条件。好处是：改口后旧确认自动失效、迟到消息不会误写、播报失败不会提前写库。验证方式是 c04、c08、c11、c13 四条用例，分别覆盖改口、重复确认、播报失败和迟到消息。

### 5.2 两级历史继承

把“档案带出的值”和“用户明确引用上次记录”分开处理：前者是候选，必须随本次复述确认；后者是明确指令，只要档案能给出唯一且相符的科室医生就直接采用。这样既不擅自替用户做决定，又能在用户明确说“还是上次那位”时省掉两轮。对照结果是继承类用例从 3 轮降到2 轮。

### 5.3 科室-医生依赖检查

把业务规则（医生属于科室）放进字段更新而不是保存前检查：换科室时立即清空不相符的医生并追问。基线的对照显示，不做这一步会把“康复科张医生”写成“骨科张医生”。这个改进点很小，但它是“字段之间有关系”这类问题的最小可行做法。

### 5.4 结构化事件 + 回放对照

五类事件与接口规范一致，回放引擎可以脚本化用户话术、注入播报失败与写库失败、投递迟到消息。它带来的不只是测试方便：同一组用例可以在基线与改进组上各跑一遍，指标由脚本统计，结论可复现。这也是本报告所有数字的来源。

### 5.5 三级实验设计

基线（固定顺序）→ 改进组（继承 + 澄清 + 依赖检查）→ 可选对照（只开关历史继承），共享同一份词表、档案、C 的解析规则和保存逻辑，只切换开关。这样“轮数变化”可以归因到具体机制，而不是笼统地说“改进了”。

### 5.6 先写库、后播报

顺序看起来是细节，但决定了失败时的用户体验：先播报后写库，一旦写库失败，用户已经听到“已登记”；先写库后播报，最坏情况是写成功但没播出来，此时可以用同一 registration_id 重新播报，不会重复登记。配套的是播报失败用新 reply_id 重发、确认只认已播完的那一条。

## 六、风险与边界

- 样本边界：本轮用户话术由组员编写，不是真人录音，也没有老年志愿者样本；轮数与成功率只代表脚本化场景。
- 理解边界：字段正确性依赖 C 的解析，D 只能通过复述确认发现问题，不能在理解层纠错。
- 设备边界：真实播报超时、设备忙、麦克风被系统声音占用等情况只做了接口级模拟，未在树莓派上实测。
- 数据边界：本地库未做断电恢复与并发写入测试，真实部署需要加 WAL 与定期备份。
- 评测边界：15 条用例覆盖了方案要求的场景，但不是统计意义上的大规模评测；结论应理解为“机制有效性”的初步证据。

## 七、小结

我在本项目中负责 D 模块，完成了从状态设计、策略实现、本地登记到评测材料的一整套工作。D 的价值在于把 C 的一串理解结果组织成一次可确认、可更正、可回滚的登记任务，并用结构化事件把 A、B、C、E 串成一轮完整的对话。

本轮的结果是：改进组 15/15 通过、字段全对、重复写入 0，继承类用例从 3 轮降到 2 轮，歧义类从 4 轮降到 3 轮并消除重复询问；代价是换科室场景多问一句。下一步先接通真实 C、E 与树莓派，再引入置信度与可学习的澄清选择，把“规则先行”的原型推进到可评测、可维护的系统。
