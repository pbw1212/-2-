# D 模块代码讲解

本文按“一次登记在代码里怎么走”的顺序讲代码：先看事件结构，再看状态载体，
然后是策略的决策流程、本地库、C 的替身、回放与评测，最后是需要改代码时
该动哪一处。配套的接口字段见 `../05_D接口与说明文档/接口样例.md`。

---

## 1. 整体分层

```
             NLU_RESULT (C)                REPLY_REQUEST (E)
                   │                              ▲
                   ▼                              │
   ┌──────────────────────────────────────────────────────┐
   │ policy.DialogManager  状态机 / 补问 / 复述 / 保存决策 │
   │        │            │             │                  │
   │        ▼            ▼             ▼                  │
   │   draft.Draft   config.*      store.RegistrationStore │
   │  （草稿与快照）（词表与开关）    （SQLite 本地登记）    │
   └──────────────────────────────────────────────────────┘
                   │
                   ▼
             TURN_CONTEXT (A/B/C)
```

- `events.py`：只定义字段与校验，不参与决策。
- `draft.py`：一次登记的全部状态（槽位、来源、版本、确认快照）。
- `policy.py`：唯一做“下一步做什么”判断的地方。
- `store.py`：只负责把确认后的结果写进 SQLite，并保证幂等。
- `config.py`：把科室、医生、档案和策略开关从代码里拿出来。
- `nlu_sim.py`：C 未接通时按规则生成同样结构的事件，方便独立调试。
- `replay.py` / `evaluation.py`：把用例跑成可复现的日志与指标。

这种分层的直接好处：C 接真实语音、E 接真实播报时，只替换事件来源，
`policy.py` 一行不用改。

## 2. 事件层：`dmodule/events.py`

```python
ev.make_event("NLU_RESULT", "s01", 2, payload)   # 补齐公共字段
ev.validate_envelope(env)                        # 校验 schema_version/轮次等
ev.validate_nlu_payload(payload)                 # 校验意图、槽位、状态
```

要点：

1. 公共字段固定为 `schema_version=1, event, session_id, turn_id,
   emitted_mono_ms, payload`，和《全组联调总方案与接口规范》一致。
2. `slot_payload(value, raw, status, candidates)` 强制“歧义时 value 必须为空、
   候选放在 candidates”，避免下游把两件事混在一个字段里。
3. 枚举集中在文件顶部（`INTENTS`、`SLOT_STATUSES`、`QUESTION_TYPES`），
   新增意图或状态时只改这里。

## 3. 状态载体：`dmodule/draft.py`

### 3.1 槽位 `Slot`

| 属性 | 含义 |
| --- | --- |
| `value` | 规范值（科室/医生用词表 ID，日期 `YYYY-MM-DD`，时段 `morning/afternoon`） |
| `raw` | 用户原表达，保留下来便于排查 |
| `source` | `user` / `history` / `history_ref` / `none`，**跨轮保留值来源** |
| `status` | `missing` / `ok` / `ambiguous` / `candidate` / `needs_check` / `skipped` |
| `candidates` | 歧义时的候选，含 `value/raw/label` |
| `updated_turn` | 最近一次修改发生在第几轮 |

`status` 是整套逻辑的关键：

- `candidate`：从档案继承来的值，算“已填”但要随本次确认一起复述；
- `needs_check`：换科室后原医生不再适用，阻塞确认直到问清楚；
- `skipped`：用户明确说“不指定医生”，不再追问，也不写进记录。

### 3.2 草稿 `Draft`

```python
draft.apply_slot("department", payload, turn, lexicon, check_dependency=True)
draft.mark_revision()          # 版本 +1，旧确认快照作废
draft.set_snapshot(reply_id, confirm_turn=turn+1, playback_done=False)
draft.snapshot_valid_for(turn) # 返回 (bool, reason)
```

`snapshot_valid_for` 同时检查三件事：版本一致、轮次一致、该回复已播完。
这就是“旧确认不能触发保存”“改口后要重新确认”“播报没完成不能算确认”的
统一实现，缺一个条件都不放行。

`apply_slot` 里还有一条字段依赖规则：科室变化时，若原医生不属于新科室，
把医生清空并标 `needs_check`。基线通过 `check_dependency=False` 关闭这一步，
用来做对照。

## 4. 策略：`dmodule/policy.py`

### 4.1 入口与去重

```python
manager.handle(env)   # 只认 NLU_RESULT / PROFILE_SUGGESTION / PLAYBACK_RESULT
```

`_on_nlu` 先做三件事：同一轮重复到达直接忽略（`duplicate_turn`）；比已处理
最大轮次更小的迟到消息忽略（`late_turn`）；会话已结束则走 `_closed_reply`，
回答“已经保存过”，不会二次写库。

### 4.2 五个分支

| 意图 | 处理函数 | 行为 |
| --- | --- | --- |
| `book` / `provide_slot` / `correct` | `_collect` | 建草稿、写槽位、带出历史候选、推进到复述或下一问 |
| `confirm` | `_confirm` | 校验快照 → `_save`；快照失效则按当前草稿重新复述 |
| `deny` | `_deny` | 确认阶段问“改哪一项”；医生问题则记为不指定 |
| `faq` | `_answer_faq` | 用 C 的 `answer_text` 作答，接回原来的补问或确认 |
| `cancel` | `_cancel` | 结束草稿，不写库 |

`no_input` / `error` 走 `_reprompt`：保留草稿、重问当前字段，连续超过
`max_reprompt` 次才退出，避免用户一次没出声就被结束登记。

### 4.3 下一问怎么选

```python
def _pending_slot(draft):
    for field in ("department", "date", "period", "doctor"):
        if 必填且未填:      return field, "missing"
        if 状态有歧义:      return field, "ambiguous"
        if 状态待核:        return field, "check"
```

固定顺序保证“缺什么问什么”。`_question` 再决定问法：

- 歧义日期且开启澄清 → “您说的是哪一周的周五？本周五（11月27日）还是下周五（12月4日）？”；
- 关闭澄清（基线）→ 退回开放式“请问您想约哪一天？”；
- 换科室后的医生 → “换到骨科后，原来的医生不再适用。请问还要指定医生吗？可以说不指定。”

### 4.4 复述与确认

```python
draft.phase = "confirming"
reply_id = "r-<session>-<turn>-<seq>"          # 每次播报一个新的 ID
draft.set_snapshot(reply_id, confirm_turn=turn + 1)
```

复述文本由已确认的规范值拼出：`为您登记复诊：康复科张医生，12月4日下午，对吗？`
同时发出 `TURN_CONTEXT`（`question_type=yes_no`），供端点检测知道下一轮是
“是/否”短答。

### 4.5 保存与失败恢复

`_save` 先写库，再播报“已登记”，顺序不能反：

```python
reg_id, created = store.save_registration(...)
if created: 文本 = "已为您登记：… 登记编号 REG-0001。"
else:       文本 = "这次登记已经保存过了，登记编号 REG-0001，不需要重复登记。"
```

写库异常时草稿和快照都保留，回一句“保存没有成功，请再说一次确认”，
重试成功仍然只有一条记录。

`_on_playback` 处理 E 的回传：`completed` 只做一件事——把快照的
`playback_done` 置真；`failed` 则用**新的 reply_id** 重发同一段文本，
并把快照改绑到新回复上。这样“重试使用新的 reply_id”和“确认只认实际播完的
那一条”两个约定同时成立。

### 4.6 历史继承

```python
self._apply_history(draft, state, turn, explicit=False)  # 建草稿时带出候选
self._apply_history(draft, state, turn, explicit=True)   # 用户说“还是上次那位”
```

- 隐式：档案里有、草稿里没有的科室/医生写成 `candidate`，随本次确认；
- 显式：只有档案能给出唯一且相符的科室与医生时才整体采用，否则留给后续按
  字段提问（`history_ambiguous` 日志）；
- 显式继承时如果用户同一轮已经说了科室或医生，以用户为准。

### 4.7 输出与日志

`_reply` 是唯一的出口：生成 `REPLY_REQUEST`，必要时再生成下一轮的
`TURN_CONTEXT`，同时把动作、阶段、期望字段写进 `dialog_log`。回放日志里能看到
每次 `slots_updated`、`confirm_rejected`、`saved` 的细节，方便定位问题发生在
哪一轮。

## 5. 本地库：`dmodule/store.py`

```sql
CREATE TABLE registrations (
  registration_id TEXT PRIMARY KEY,   -- 一次确认一条
  session_id TEXT, profile_id TEXT,
  department TEXT, doctor TEXT,
  visit_date TEXT, period TEXT,
  created_at TEXT, snapshot_json TEXT, source_json TEXT);

CREATE TABLE dialog_log (...);        -- 每轮状态变化与动作
```

- `save_registration` 先查同 ID 是否已存在，再 `INSERT`；`IntegrityError` 时回滚
  并按“已存在”处理，返回 `(id, False)`。
- 只有 `commit()` 成功才返回，调用方据此决定播报“已登记”。
- `source_json` 保存每个字段的来源（user/history/history_ref），回放时可以
  核对“这个值是从哪来的”。
- `has_duplicates()` 是评测里的“重复写入检查”。

## 6. C 的替身：`dmodule/nlu_sim.py`

C 未接通时，用规则把一句话解析成同样结构的 `NLU_RESULT`：

1. `_norm` 统一全半角、去空格，但保留“不”“改”等影响意图的字；
2. 先判取消、否定、改口，再抽字段；
3. `_parse_date` 支持“今天/明天/后天/下周X/本周X/周X/12月4日”，
   没说周次的“周五”返回 `ambiguous` 和两个候选；
4. FAQ 用关键词命中 `config/faq_stub.json`，返回 `faq_id/answer_text/score`。

它的定位是**测试替身**，正式联调时整段替换成 C 的输出即可。

## 7. 回放与评测

`replay.CaseRunner.run` 做四件事：

1. 新建 `DialogManager`，从 `steps` 逐条发送 `NLU_RESULT`；
2. 每收到 `REPLY_REQUEST`，立即回传 `PLAYBACK_RESULT completed`（用例可要求先
   `failed` 一次）；
3. 用返回的 `TURN_CONTEXT` 推进轮次，把每轮上下文交给替身解释短答；
4. 结束后比对“预期记录条数 / 预期字段”，并统计用户轮数与重复询问。

`evaluation.run_suite` 用同一组用例跑两套配置：基线
（`inherit_history=False, clarify_ambiguous=False, check_slot_dependency=False`）
与改进组（默认全开）。`aggregate` 计算成功率、轮数中位数/均值、重复询问、
字段正确率、重复写入行数，以及四个场景分组的对照。

| 需求 | 改动位置 |
| --- | --- |
| 新增科室/医生 | `config/lexicon.json` |

| 新增用例 | `cases/*.json`，加 `expect` 即可 |
| 改评测口径 | `evaluation.aggregate` |

## 9. 代码约定

- 只用标准库，树莓派上不需要额外安装；
- 事件字段名与接口规范一一对应，新增字段放在 `payload` 里且不改变已有语义；
- 所有状态修改都经过 `Draft`，不在 `policy` 里直接改字典；
- 任何会改变登记内容的操作都必须 `mark_revision()`，让旧确认失效；
- 写库成功才允许播报“已登记”。
